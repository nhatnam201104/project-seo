# PostgreSQL Backend Foundation, Auth, and Public Catalog

## Intent

Create the first Spring Boot backend module for ProjectSale using Java 21 and PostgreSQL, while retaining the current DBML's business model as the source of truth and recording user-approved schema additions in Flyway. Deliver a production-oriented, feature-based foundation, database-backed JWT refresh sessions, and the public catalog APIs already consumed by the frontend, without exposing JPA entities or sequential database IDs.

## Decisions

- PostgreSQL is the database target confirmed by the user. `database/schema.dbml` remains unchanged as the historical MySQL-oriented business-model reference; Flyway migrations become the executable PostgreSQL schema source. Public API documentation is updated to reflect the approved UUID and refresh-rotation contract changes, using the repository backup policy.
- Use one modular monolith module in `backend/`, keeping each implemented feature cohesive. The initial implemented feature is `catalog` (product, category, brand, variant, image); common infrastructure contains configuration, API errors, response types, security baseline, and pagination.
- Create the full documented relational schema in Flyway so later features have stable foreign-key targets. Create Java persistence code for `auth`, `user`, and catalog tables only in this increment.
- Implement public endpoints: product list/search/detail/related, category list/tree/detail, and brand list/detail. Implement the existing auth contract: register, login, refresh, logout, and current-user. Administrative writes, carts, checkout, payments, reviews, and media upload are deferred.
- Spring Security is stateless: access tokens are signed JWTs and refresh tokens are cryptographically random opaque values stored only as SHA-256 hashes in PostgreSQL. Refresh token rotation, expiry, revocation, and logout are supported; raw refresh tokens and raw access tokens are never persisted.
- Access JWTs use HS256 with a base64-encoded, at-least-256-bit `JWT_SECRET_BASE64` supplied only by environment configuration; `issuer=projectsale-api`, `audience=projectsale-web`, access TTL 15 minutes, refresh TTL 30 days, and allowed clock skew 60 seconds. The authentication filter verifies signature, issuer, audience, expiry, and then verifies that the subject user still exists, is ACTIVE, and is not soft-deleted; no key or secret is committed to source control.
- Use PostgreSQL `BIGINT GENERATED BY DEFAULT AS IDENTITY`, `TIMESTAMP WITH TIME ZONE` mapped to `Instant`, `NUMERIC(12,2)` mapped to `BigDecimal`, and PostgreSQL enum types matching the DBML enums. Hibernate uses `ddl-auto=validate`; schema changes occur only via Flyway.
- Retain each original `BIGINT` primary key as an internal technical key. Add `public_id UUID NOT NULL UNIQUE DEFAULT gen_random_uuid()` to every entity exposed through current or planned HTTP APIs. DTOs, JWT subject claims, and all URL/request references use `public_id`; internal IDs never leave the API.
- Add user-requested catalog metadata to `products`: nullable `gender VARCHAR(32)`, non-null `has_lens BOOLEAN DEFAULT FALSE`, and non-null `face_tags VARCHAR(32)[] DEFAULT '{}'`. `gender` remains a constrained string rather than a Java/PostgreSQL enum because no allowed vocabulary exists in the source requirements; face tags are a PostgreSQL array because one product can fit multiple face shapes, with a GIN index for filtering.
- Keep the frontend's established response contract: snake_case JSON body fields and the Spring-page-shaped `{ content, totalElements, totalPages, number, size }` response. Query parameters stay camelCase; pagination defaults to `page=0,size=20`, permits sizes 1–100, and sorting accepts only `createdAt`, `minPrice`, or `name` in `field,asc|desc` form (default `createdAt,desc`). Invalid ranges, pagination, and sorting return a validation error.
- Translate the documented MySQL FULLTEXT note into PostgreSQL full-text search using a GIN expression index over `to_tsvector('simple', name || ' ' || coalesce(description, ''))` and use that exact expression with `websearch_to_tsquery('simple', q)` in the query. This supplies the documented MUST `/products/search` endpoint without adding undocumented schema fields; Vietnamese diacritic-insensitive search is deferred until a product requirement selects an extension/configuration.
- Public catalog visibility is `status = ACTIVE` and `deleted_at IS NULL`. Product price filtering applies to the documented denormalized `products.min_price`; color filtering is case-insensitive and uses an `EXISTS` condition over non-deleted variants, preventing duplicate products. `gender` matches case-insensitively, `hasLens` matches the boolean, and `faceTag` uses PostgreSQL array containment.
- Related products are up to four other visible products in the same category, ordered by `rating_avg DESC`, `created_at DESC`, then `id DESC`. A non-visible or unknown source slug returns 404.
- Category responses expose `id`, `name`, `slug`, `image_url`, and `parent_id`; category detail additionally exposes `meta_title` and `meta_description`. The tree adds recursive `children`, ordered by `name ASC`, and is built from visible categories only. Brand list responses expose `id`, `name`, `slug`, and `logo_url`; brand detail additionally exposes `info`, `meta_title`, and `meta_description`. Unknown or non-visible slugs return 404.
- The standard error payload is `{ timestamp, status, error, code, message, path, correlationId, fieldErrors }`; the last two are nullable/omitted when unavailable. Success DTOs use snake_case; the two error fields retain their established camelCase names through explicit JSON-property annotations. `X-Correlation-Id` is echoed/generated per request.
- A refresh token is at least 256 CSPRNG bits, base64url encoded, and has a SHA-256 hash stored at rest. Refresh uses a transaction with row locking: it accepts only the current, unexpired, non-revoked record; revokes it and creates one replacement atomically; detected reuse revokes the whole token family. Unknown, expired, and revoked tokens all return the same 401 response. Logout requires an authenticated subject owning the session and revokes that token family.
- Because rotation returns a new refresh secret, `/auth/refresh` returns `{ access_token, refresh_token }`. The frontend API type, SSR refresh bridge, and API document will be updated together. Public UUIDs likewise require the frontend `Id` type, query parsing, DTO types, and API documentation to change from numeric IDs to UUID strings; this is a deliberate API-contract migration.
- `face_tags` values are normalized to canonical lowercase at write time and `faceTag` is normalized to lowercase before PostgreSQL array containment filtering. The vocabulary remains unconstrained until admin catalog writes define it.

## Approach

The backend will begin as a self-contained Maven Spring Boot project with reproducible PostgreSQL development infrastructure and Flyway-owned schema. It will translate the existing data model and the approved auth/public-ID/catalog additions into PostgreSQL before mapping the auth and catalog tables with JPA and MapStruct. Auth will issue short-lived JWT access tokens and rotate database-backed opaque refresh tokens, while public catalog queries use DTO projections or targeted fetches to avoid N+1 behavior. Tests will cover token lifecycle, services, HTTP validation/error behavior, and PostgreSQL-backed repository queries through Testcontainers.

## Scope

**In:** Maven/Spring Boot project baseline; Docker Compose PostgreSQL; Flyway schema for the documented tables/enums/constraints/indexes including `pgcrypto`, the PostgreSQL FTS index, and approved additions; common error response and correlation ID; OpenAPI; auth/register/login/refresh/logout/me; public catalog APIs; auth/user/catalog entities, repositories, services, DTOs, mappers, specifications/projections as needed; synchronized frontend UUID and refresh-rotation contract updates; API/documentation contract updates; unit, controller, frontend typecheck, and PostgreSQL Testcontainers tests; CI workflow.

**Out:** changing the existing DBML; any admin mutation endpoint; seed data; carts, checkout, orders, payments, promotions, reviews, wishlist, blog, notifications, upload/object storage; database backup automation.

## Future Notes

Forgot/reset-password is marked MUST in the existing API document but requires an email-delivery provider and a password-reset token lifecycle, neither of which is configured in this repository. It remains a deliberate deferred-contract exception in this increment. Admin catalog writes should be added after the initial auth/RBAC baseline; then define an allowed vocabulary for `gender` and `face_tags` and enforce it in request validation.

## Review

_Filled in after completion._

- PostgreSQL `CHAR(64)` and JPA `String` caused a strict Hibernate validation mismatch; using `VARCHAR(64)` preserves the SHA-256 hex invariant while keeping `ddl-auto=validate` reliable.
- Database-generated UUID defaults are not automatically available on a newly persisted user before refresh; assigning the user public UUID in `@PrePersist` keeps registration/JWT issuance deterministic while retaining the database default as a safety net.
- Hibernate's PostgreSQL array predicate needs an explicit `array_position(...) > 0` comparison; integration coverage with a nonmatching tag prevents a false-positive filter implementation.

## Implementation Notes

- Create `backend/` rather than mixing Java sources with the React application. Use Java 21 discovered locally and a currently supported Spring Boot 3.x release.
- Relevant source contracts: `database/schema.dbml`, `docs/database-documentation.html`, `docs/api-list.html`, and `frontend/app/features/catalog/api/product.types.ts`.
- Flyway enables `CREATE EXTENSION IF NOT EXISTS pgcrypto` before any `gen_random_uuid()` default. Add public UUIDs table-by-table to every documented API-facing table, retaining original bigint keys/FKs as internal implementation details.
- Catalog tables: `categories`, `brands`, `products`, `product_variants`, `product_images`; dependent schema tables must use the documented FK actions in DBML. `products` adds `gender`, `has_lens`, and `face_tags` per the approved extension.
- Auth tables: retain `users`; add `refresh_tokens` with internal identity `id`, UUID `public_id`, `user_id` FK (`ON DELETE CASCADE`), unique `token_hash` (SHA-256), `token_family_id UUID`, `expires_at`, nullable `revoked_at`, nullable `replaced_by_token_id` self-FK, `created_at`, and nullable `last_used_at`. Index `(user_id, expires_at)` and `token_family_id`. A refresh exchange atomically revokes the used token and issues its replacement; reuse of a revoked token revokes its token family.
- JWT access-token claims: subject is `users.public_id`, role is the DBML role string, issued-at/expiry/jti are standard claims. Access tokens are short-lived and not stored in the database; refresh tokens are long-lived opaque secrets, returned once in the documented JSON body and stored only hashed.
- All request/response IDs and every endpoint that uses an `id` path/query parameter use public UUIDs. Product/category/brand public detail remains slug-based; `ProductVariant` response uses its `public_id` as `variant_id` so it remains frontend-compatible in field name while changing value type from numeric to UUID.
- Update frontend `app/core/domain/enums.ts` `Id` to UUID string; update catalog query parsing and types, auth user ID types, and refresh interceptor contracts so `/auth/refresh` persists the rotated `refresh_token`. Update `docs/api-list.html` responses and auth refresh contract. Before modifying an existing documentation or frontend source file, create a timestamped backup under `backups/` and remove it within one week after successful verification, as required by the repository instructions.
- Public routes: `GET /api/v1/products`, `GET /api/v1/products/search`, `GET /api/v1/products/{slug}`, `GET /api/v1/products/{slug}/related`, `GET /api/v1/categories`, `GET /api/v1/categories/tree`, `GET /api/v1/categories/{slug}`, `GET /api/v1/brands`, `GET /api/v1/brands/{slug}`.
- Auth routes: `POST /api/v1/auth/register`, `POST /api/v1/auth/login`, `POST /api/v1/auth/refresh`, `POST /api/v1/auth/logout`, and `GET /api/v1/me`. Register/login/refresh are public; logout and `/me` require a valid access JWT.
- Product list accepts schema-backed filters only: `categoryId`, `brandId`, `minPrice`, `maxPrice`, `color`, `gender`, `hasLens`, `faceTag`, `page`, `size`, `sort`. `categoryId` and `brandId` are UUID public IDs. `minPrice`/`maxPrice` bound `products.min_price` inclusively and `minPrice <= maxPrice`; color searches non-deleted variants case-insensitively; gender matches case-insensitively; `hasLens` matches the boolean; `faceTag` uses array containment. The default page is 0/20, maximum size 100; negative page, invalid size, malformed or non-allowlisted sort return 400.
- Product search requires nonblank `q` of at least two characters, shares pagination/sort rules with the list, and returns only visible products. The `simple` PostgreSQL text-search configuration is an intentional first increment choice.
- No SQL migration or seed data exists today. DBML intentionally targets MySQL, so PostgreSQL equivalents require explicit review: enum types, identity keys, `timestamptz`, standard/GIN indexes, `reviews.rating` check 1..5, and `smallint` replacement for MySQL `tinyint`; preserve each documented FK delete action.
